# M3 性能与容量报告

测试环境为 16 逻辑核 CPU、FP32 BGE Reranker。外部 LLM 被本地固定响应替代，因此结果仅表示检索服务，不包含供应商生成延迟。

| 场景 | p50 | p95 | 错误率 | 结果 |
|---|---:|---:|---:|---|
| 8 个相同冷请求 | 约 14.78 s | 14.79 s | 0 | 通过冷启动门槛，7 个请求被合并 |
| 8 个相同缓存热请求 | 19.48 ms | 23.74 ms | 0 | 通过 |
| 模型已加载、不同 exact 单请求 | 5.42 s | 5.54 s | 0 | 通过 8 s 门槛 |
| 5 个不同 exact 并发 | 15.67 s | 24.64 s | 0 | 未通过 8 s 门槛 |

## 已实施优化

- 相同未缓存请求进行 in-flight 合并，避免缓存击穿；
- 本机默认使用 12 个 PyTorch CPU 线程；
- CrossEncoder 默认单路推理，避免多个 12 线程任务互相争抢；
- 本地检索并发限制为 2，并分别记录检索队列和 Reranker 队列耗时；
- 容器启动时预加载索引和 Reranker，把模型冷启动移到服务就绪之前；
- 保留 FP32。INT8 试验虽然把 20 候选推理从约 4.18 秒降到 3.15 秒，但改变了 Top 5 排序，未作为默认方案。

## 容量结论

当前 CPU 主机适合单个重查询或大量重复、可缓存查询。5 个不同的重查询同时到达时，p95 约 24.64 秒，因此 M3 状态为 `needs_hardware_or_scale_out`。

若要求 5 并发下 p95 小于 8 秒，建议使用 GPU Reranker，或部署多个独立 API 副本并由负载均衡器分流。增加同一进程内的 CPU 推理并发只能小幅提升吞吐，同时会恶化单请求延迟。
